# RELAY Desk 設計メモ

## 目的と範囲

問い合わせの属人化、資料の散在、AI回答をそのまま採用する危険を、1つのレビュー経路で扱うポートフォリオ。
「根拠資料を見つける→下書き→人が確認→承認」の履歴を保存する。
v0.2はテキスト資料が対象。高度なRAG、PDF抽出、顧客への送信、実業務導入は未完了。

## 構成

ReactはFastAPIと同一Originで配信し、クロスオリジンのCookie運用を避ける。
SQLAlchemyでSQLite開発とPostgreSQL向け構成を共通化。PostgreSQLは別途検証が必要。
SitesのホスティングはWorker実行環境であり、今回合意したPythonサーバーをそのまま動かす構成ではないため、ソース一式として納品する。

| テーブル | 役割 |
|---|---|
| tenants | 企業、企業内変更の直列化用カウンター |
| users | 企業・ロール・Argon2ハッシュ |
| sessions | セッショントークンのSHA-256・CSRF・8時間期限 |
| login_attempts | アカウント単位8失敗/15分の制限 |
| tickets | 問い合わせ、担当者、状況、更新版 |
| articles | 現在の資料、公開状態、版 |
| article_revisions | 保存時ごとの本文スナップショット |
| drafts | リクエストID、元問い合わせ版、資料抜粋、生成原文、レビュー結果 |
| audit | 操作者・時刻・対象・操作・変更概要 |

企業をAPIクエリで必ず絞り込む。子レコードの企業IDと親の企業IDは複合FKで一致させる。
RLSは実装していない。DBへ直接アクセスする管理者の権限まで隔離する設計ではない。

## 状態と競合

問い合わせは未対応・対応中・完了。完了には現在の問い合わせ版と資料版に対応した承認が必要。
担当/状況変更でも版を増やす保守的な設計。完了後に再開した場合は新しい生成・承認が必要。
下書きはgenerating→draft/blocked/failed、draft→approved/rejected。承認の上書きは禁止。
資料は版を増やし旧本文を保持。承認操作は公開中か、参照版が一致するかを再検証。

企業行のUPDATEで、資料更新・問い合わせ変更・生成予約・承認を企業内で直列化する。
AI呼び出しの前に予約をcommitし、外部待ちの間はDBロックを解放する。
戻った後に結果を保存し、Cookieセッションが有効か再確認してから返す。
同じ企業・request_keyは一意。再送時は同じ結果を返し、追加の課金を伴う呼び出しをしない。
24時間上限は予約・失敗も数える。2分以上経過したgeneratingはレビュアーが手動復旧できる。生成完了保存も企業ロック下で状態を再確認し、復旧後の遅延応答は保存しない。自動回復ジョブは未実装。

## 検索・AI境界

初期実装はNFKC正規化→空白除去→2文字単位のcosine類似度。0.10以上、上位3資料。
埋め込みやベクトルDBは未使用。最大500資料を段落ごとに分割し、長い段落は800文字・200文字重複のチャンクに分ける。各資料で最も関連する1チャンクを採用。抜粋のoffsetと資料版を保存する。
同義語・指示語・複雑な条件解釈には不十分。固定7問と長文ケースの回帰テストを追加したが、本格的な検索品質評価は今後。
スコアは文字の類似度であり確信度ではない。UIでも正確性の指標として扱わない。

プレビューは質問本文と資料抜粋を表示し、そのSHA-256を生成要求で照合。
表示後に資料が変われば409で再確認を求める。
本文内のPII自動匿名化はないため、初期版は架空データ限定。顧客名欄は送信しない。

OpenAIは固定の公式Responses APIへ送信。store=false、出力上限1600tokens、HTTPXの各タイムアウト25秒、応答サイズ128KiB、リダイレクト・自動リトライなし。
JSON Schema・Pydantic・許可引用IDの検証を重ねる。資料内の命令は信頼しないよう指示し、ツール実行機能は提供しない。
形式検証だけで幻覚やプロンプトインジェクションを完全に防げるわけではない。人の確認が最終境界。
HTTPXのタイムアウトは総処理時間の厳密な上限ではない。長時間処理のジョブ化は今後の対象。

参考（2026-10-16確認）：https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses

## 制限と安全上の残作業

- 監査・過去資料はAPIから編集不可。ただしDBレベルの改ざん防止トリガーや外部保管は未実装。
- SSO/MFA・招待・パスワード再設定・ユーザー無効化UI・セッション一覧は未実装。
- ログイン試行制限は小規模デモ向け。IP制限、同時リクエスト制御、WAFは未整備。
- 最新200問い合わせ/500資料/150監査の上限。ページング・サーバー検索は今後。
- リトライ時の二重生成抑止はAPIのrequest_key単位。フロントは通信失敗時に同じキーを保持するが、再読込・再ログイン後は履歴確認が必要。
- 本番用ロール分離・RLS・PostgreSQLバックアップ復元・監視・保守手順・負荷試験は未整備。
- UIはレスポンシブCSSとキーボード操作を実装したが、視覚QA/アクセシビリティ実機検証は未実施。
